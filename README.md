# Legacy API Migration Advisor

**This repo contains two implementations of the same product idea.** V1
(Java / Spring Boot / Spring AI) is complete and preserved as-is. V2 — the
product rethink, on a new stack — is the current work, and is what this
README is about.

## What V2 is

Migration Compass assesses a legacy codebase's readiness for migration and
answers the question a team actually has before committing to one: *how bad
is this, and what will it cost?*

You upload a source archive. The app indexes it, runs a multi-agent
analysis over it, and puts five scores, an **analysis report** that explains
them, per-service findings, the evidence behind every score, and a dependency
graph on **one page** — no tabs, no report to export, no dashboard to
navigate. Optional operational data and migration parameters refine those
numbers in place, and the same app renders its own OpenTelemetry traces.

Two routes carry the product: **`/`** (upload, projects, analysis, scorecard,
analysis report, dependency graph, refinement, ask bar) and **`/admin/traces`**
(span waterfalls), plus `POST /api/ask` for the streaming answer endpoint.

The problem it solves: migration assessments are normally either a senior
engineer's verbal estimate ("call it six months") or a consultant's deck
produced over weeks. Both are unauditable. Here every number is computed
from persisted structured findings by a documented rubric, and every score
can be expanded to show the arithmetic that produced it.

### The five scores

| Score | Range | What it is |
| --- | --- | --- |
| Migration Readiness | 0–100 | Inverse composite: risk, effort, restructuring, coverage gaps and data-quality issues pull it down; an explicit "architecture is largely sound" finding pulls it up |
| Risk | 0–100 | Weighted mean of per-service risk levels (critical 100 / high 75 / medium 50 / low 25), equal-weighted or dependency-weighted |
| Effort | 1–10 | Four weighted terms: service count (0.3), migration phases (0.2), risk (0.3), major restructuring (0.2), with a floor of 1 |
| Cost | USD | Person-weeks × team size × a blended weekly rate — from assumptions shown in the UI, not hidden constants |
| Time | weeks | Derived from the Effort band (1–2 → 4–8 weeks … 9–10 → 9–12+ months), then adjusted sublinearly by team size |

**No score is generated by a model.** The scoring engine is pure,
dependency-free TypeScript under `v2/src/lib/scoring/` — no React, no
Next.js, no database, no network. The same input always produces the same
scores. The model produces *findings*; the rubric produces *numbers*.

### Confidence and explanations

Every score carries a **`code-only estimate`** tag, or **`refined with
operational data`** once measured operational data has moved a number. Neither
implies a model: the refinement parses the files you attach deterministically,
and the UI says so.

Alongside the tag sits an **evidence quality** signal derived deterministically
from what was actually available: `strong` (services, typed dependency edges and
an architecture output all present), `partial` (something is missing — and the
missing thing is named), or `limited` (no findings at all). The reasons are
listed in the UI, so a confidence tag can be traced rather than taken on faith.

Expanding any score shows its actual contributions: for the additive
rubrics (risk, effort, readiness) the rows are labelled and sum to the
score within a rounding tolerance, and the UI says so — or says the
opposite if they ever stop summing. For a refined scorecard the operational
terms appear as their own rows, attributed to measured data rather than to
a finding, and each score shows what it was before refinement.

### The analysis report — the explanation layer

The scorecard is the executive summary: five numbers, their confidence tags and
the arithmetic behind each one. Beneath it sits the **analysis report**, which
answers the questions a number cannot: what was discovered, why the scores are
what they are, and what the migration considerations are.

It is **composed, never generated**. There is no second LLM pass over the
codebase — the report is assembled on the server from data the analysis already
persisted: the four validated structured outputs (`discovery_output`,
`architecture_output`, `risk_output`, `comparison_output`), the per-service
findings, the dependency edges, the indexed source inventory, and the same
deterministic rubric arithmetic the scorecard shows. Its estimate section prints
the scorecard's own figures through the same formatter, so the two cannot
disagree.

Eight sections, in reading order:

| Section | What it states |
| --- | --- |
| Executive Summary | What was discovered, the migration posture, the most serious recorded concern, and the recorded migration direction — always visible, not behind a disclosure. Presented as a lede paragraph beside its supporting paragraphs, with the highlighted findings below it as two-up **key takeaway** cards |
| System Discovery | Services with their structured traits, technology stack, storage, messaging, external integrations, runtime issues |
| Architecture Analysis | The most depended-upon services, the longest dependency chain, circular chains, shared-database coupling, unclassified edges, services with no recorded relationships — read from the same graph model the diagram below renders |
| Risk Analysis | Every finding by severity, with the Risk stage's reasoning, the rubric's level values and the evidence each rating rests on |
| Findings by Service | The same findings the other way round: one disclosure per service, with its severity, rubric inputs, the Discovery stage's recommendation, cited risk factors, the evidence source behind the rating, and what it calls and is called by. Services that appear only in the edges are listed as unrated, not omitted |
| Migration Considerations | Straightforward areas, services needing restructuring, coverage gaps, and the recorded phased plan in phase order |
| Effort and Cost Explanation | Effort, cost and time with the rubric's own contributors, the assumptions in force, and the operational-data adjustment when refinement data exists |
| Evidence | Supported by indexed source file names (never their contents), cited risk factors, per-edge static-analysis evidence, an explicit evidence-quality statement, and the Comparison stage's self-assessment |

Progressive disclosure is the whole interaction model: the executive summary and
the **key takeaways** are on screen, every section is a `<details>` that expands in place,
and each section states one line about what it holds while collapsed. Sections
with nothing to say say so rather than rendering an empty box, and severity is
always stated in words as well as colour.

The dependency topology is readable without the graph as well: the same graph model
the canvas draws is rendered as a text list of edges, services and cycles, so screen
readers, copy-paste and the graph's known edge-rendering defect all have an answer.

Any section, and any individual finding, carries an **Ask about this** control
that hands a composed question to the existing ask bar — it selects the project,
prefills the box, shows which section the question came from and takes focus. The
reader still presses Ask, so no model call happens as a side effect of reading.
There is one conversational surface, and it is the one that talks to `/api/ask`.

No new persistence was required for any of this, and no migration was added: the
report reads what the pipeline already writes.

## Quick Start

### Prerequisites

- **Node 20.9+** (Next.js 16 requirement; verified here on Node 24.3.0)
- **pnpm** (verified on 11.25.0)
- **Docker** with Compose (verified on Docker 29.7.2 / Compose v5.3.1)

### Start infrastructure

Two containers, both defined in `v2/docker-compose.yml`:

```bash
cd v2
docker compose up -d postgres
docker compose up -d ollama
docker compose exec ollama ollama pull nomic-embed-text
```

Postgres is `pgvector/pgvector:pg17` (container `compass-postgres`, port
5432). Ollama serves embeddings locally (container `compass-ollama`, port
11434); the model pull is a one-time step.

### Configure environment

```bash
cp .env.example .env
```

Then edit `.env`:

- `DATABASE_URL` — the example ships with a **masked** password
  (`postgres://compass:***@localhost:5432/compass`). Replace `***` with
  `compass`, which is what the compose file provisions. Leaving the mask in
  place is the most likely first-run failure.
- `DEEPSEEK_API_KEY` — required only for the narrative agent paths. The
  scorecard works without it.

### Install and migrate

```bash
pnpm install
pnpm db:migrate
```

### Load sample project

Runs a checked-in legacy fixture through the real ingestion pipeline — no
ZIP to prepare by hand:

```bash
pnpm seed:sample
```

It is idempotent (a second run reports `Reused` rather than creating a
duplicate), needs no LLM, and prints the session cookie to set so your
browser can see the project it created. See
[Sample fixture](#sample-fixture) for details.

### Run the application

```bash
pnpm dev
```

Open **http://localhost:3000**. To see the seeded project, set the cookie
the seed command printed, in the browser console:

```js
document.cookie = "mc_owner=sample-fixture; path=/"
```

Then reload: the project appears with a **Run analysis** button. Once a run
completes, the row expands into the scorecard.

### Verification

```bash
pnpm typecheck    # tsc --noEmit
pnpm lint         # eslint
pnpm test         # vitest; database-backed suites skip themselves without DATABASE_URL
pnpm test:integration   # the live-database suites
pnpm build        # production build
```

To run the database-backed suites too, set `DATABASE_URL` (the compose
password is `compass`) — the suites skip themselves without it.

Recorded results from this working tree, so you know what "passing" looks

- Since then the work has been run in groups rather than as a suite: the M7 report

## Architecture

A single Next.js process. Postgres is the only state store — projects,
chunks, runs, findings, dependency edges, scorecards and trace spans all
live in one database, so there is no separate tracing or vector service to
run.

```
upload / ask ──► Next.js App Router (one continuous page)
                    │  Server Actions for mutations, /api/ask for the SSE stream
                    ▼
             pure core + injected edges
   ingestion · embeddings · RAG · agents · scoring · graph
                    │  model, database, tools all injected — never imported
                    ▼
        PostgreSQL 17 + pgvector (projects, chunks, runs,
        findings, service_dependencies, scorecards, trace_spans)
                    ▲
             Ollama (embeddings)   DeepSeek (narrative agents)
```

Routes: one page (`/`) holds the whole assessment — upload, project list, run state,
scorecard, report, graph, refinement and the ask bar; `/admin/traces` is the
operations-only trace viewer; `POST /api/ask` is the streaming answer endpoint; and a
project action aimed at a project the session cannot see renders a not-found boundary
rather than leaking whether it exists. There is no per-project route — everything
expands in place.

Design rules that shape the code:

1. **Pure logic stays dependency-free.** Chunking, scoring, the graph model
   and the critique/refinement policies are plain functions — the reason
   the scoring tests need no database, model or network.
2. **Edges are injected.** No module-level model or database client. Every
   capability asks for exactly what it needs and fails naming the missing
   variable.
3. **Structured output is validated, never trusted.** Agent output is parsed
   with zod schemas before it is persisted.
4. **Per-run data is per-run.** Dependency edges and findings carry both
   `projectId` and `runId`, so re-analysing a project adds a comparable
   second result instead of overwriting the first.
5. **No auth/RBAC, deliberately.** Ownership is anonymous and session-scoped: a
   random `ownerId` in an httpOnly cookie (`mc_owner`, 30 days), minted on the
   first create path and filtered on every read. There is no account, no login,
   no OAuth provider, no magic link and no RBAC anywhere in the codebase — the
   id is a visibility scope, not a credential, and it is why the seed command
   prints a cookie rather than making a fixture globally visible.

### Presentation and theme

One design vocabulary, defined once in `v2/src/app/globals.css` and consumed through
CSS custom properties. Components contain **no colour literals** — a theme change is a
token change.

- **Surfaces, four and no deeper.** Page (`#070b16`, deep navy rather than black),
  panel (`#121a2e`), raised tile (`#1e2745` — scorecard metrics, takeaway cards, graph
  nodes) and an inset well (`#0b1120` — code blocks, the graph canvas). Adjacent
  surfaces differ by roughly 6.5 points of CIE L*, which is what makes the hierarchy
  visible rather than nominal.
- **One accent, one secondary, one semantic ramp.** Indigo `#8b96ff` carries actions,
  links and selected state; muted cyan `#63c9dd` appears only where a second hue is
  informative (asynchronous edges); and the `--risk-*` ramp is the *only* semantic
  palette — success, warning, error and "unrated" all resolve to it, so "critical"
  cannot look like two different reds. Every text colour clears WCAG AA on the surface
  it is used on.
- **Shared primitives, not per-component styling.** `.panel` / `.tile` / `.well`,
  `.eyebrow` / `.caption` / `.meta` / `.measure`, `.report-measure` / `.report-prose` /
  `.report-lede`, `.btn` with `primary` / `secondary` / `ghost` / `quiet-danger`,
  `.chip-accent`, `.row-disclosure` with a rotating `.marker`, `.masthead-rule` and
  `.note` — plus a global `:focus-visible` outline, because focus that a control
  styles itself is focus half the controls forget.
- **The report is a chapter, not an article.** Its container spans the dashboard and
  the bands inside it use that width — an executive summary split lede-beside-support,
  key takeaways as a two-up card grid, findings as rows with their evidence in a right
  column — while readability is enforced on the text itself by a ~79-character measure.
  Width and measure are separate decisions, and the earlier version that capped the
  *container* is why that distinction is written down here.

### M3 — the agent workflow

Orchestrated with LangGraph.js as a typed state graph, not a sequence of
function calls:

```
START ──► Discovery ──┬──► Architecture ──┐
                      └──► Risk ──────────┴──► Comparison ──► END
```

Discovery inventories services and the dependency edges between them;
Architecture and Risk both consume that result, run **concurrently**, and
both fan in before Comparison evaluates the analysis against its own
findings. Each stage drafts narrative, is critiqued once (bounded
structurally, not by a loop), and extracts a validated structured object.
The structured outputs are persisted alongside the narratives — which is
what lets M4 score without re-parsing prose.

### M4 — scoring and the dependency graph

- **Scoring** consumes persisted findings, persisted edges, the
  Architecture/Risk/Comparison structured outputs and run metadata.
  Nothing re-runs Discovery, and nothing re-derives dependencies from
  source text.
- **Risk weighting** supports both documented modes: `equal`
  (v1) and `dependency`, where a service weighted by how many other
  services depend on it carries more influence. With no edges recorded the
  two modes are identical by construction.
- **The dependency graph** is built from the persisted
  `service_dependencies` rows for a run: typed edges (synchronous call,
  async/event, shared database, external API, unclassified), nodes coloured
  by the persisted risk level, deterministic layered layout, pan/zoom and
  click-to-expand. A service that appears only as an edge endpoint is drawn
  as *unrated* rather than being given a risk level it never had. **Its
  rendering is defective: node boxes are correct, but the edge paths arc above
  the node row instead of joining node to node, and the canvas keeps unused
  height — see Known limitations.**

### M5 — operational data and refined estimates

The fast path needs nothing beyond the upload. Two optional enrichments sit
behind collapsed disclosures, and neither ever blocks the five scores:

- **Operational data** — attach logs (`.log`), health/traffic JSON (`.json`) or
  incident reports (`.md`, `.txt`), either at upload or later from the
  scorecard. These are measured facts about the running system, so they move
  **Risk**, and they move it **both ways**: healthy measurements lower it,
  degraded ones raise it, always bounded to ±15 points. Metrics drive the
  adjustment (error rate, availability, incident history, error density in
  logs); restart counts and database size are reported next to the adjustment
  but deliberately not scored. Files accumulate, and removing them restores the
  code-only estimate.
- **Migration parameters** — target environment, provider, team size, blended
  weekly rate, budget and timeline. Team size and rate feed the existing cost
  and time formulas (no constant is restated in the UI); budget and timeline are
  compared *against* the estimate and reported as conflicts, because a small
  budget must not silently produce a small cost.

**`Refine these estimates`** recalculates the five numbers in place —
synchronously, deterministically, with no model call, no retrieval and no
network. It is a different action from **Run analysis**: the recalculation
returns numbers and cannot return a narrative, because it never receives one.
Discovery, Architecture, Risk and Comparison prose, and the per-service
findings, stay exactly as the analysis produced them until someone explicitly
re-runs the analysis. That split is asserted in tests by a call-counting model
stub, a call-counting embedding stub and a `fetch` stub that fails if touched.

### M6 — traces

Every request, agent step, model call and database query is instrumented with
OpenTelemetry, and the spans are written into the same Postgres as the
application data — no separate tracing container. **`/admin/traces`** renders
them as waterfalls: trace identity, span hierarchy, durations, timestamps,
status and attributes, with each span expandable in place.

A deterministic **fixture trace** is always rendered on that page, labelled as
synthetic, so the surface can be reviewed without an analysis run, an API key or
even a database. It contains the structures a real trace goes wrong in — an
orphan span whose parent was never written, out-of-order rows, an error span,
overlapping siblings — and the page states plainly when a trace is incomplete
instead of drawing a confident-looking waterfall over it.

Credential-shaped attributes (`authorization`, `apiKey`, `cookie`, tokens,
secrets, passwords, and values that look like keys or JWTs) are replaced before
rendering, and the withheld keys are listed per span. The page is an operations
surface gated behind `ADMIN_TRACES_ENABLED`, **not** an authorization boundary:
spans carry no owner id, and the page says so.

### M7 — the analysis report, and how numbers and prose stay consistent

`v2/src/lib/report/builder.ts` composes the report as a **pure function** over
the persisted analysis: validated structured outputs, findings, dependency
edges, the graph model and the scorecard. It imports no model client and performs
no fetch — a test asserts that on the module's own source. `v2/src/components/analysis-report.tsx`
renders the finished value; it is a client component only because the ask
controls need a click handler.

Two consistency rules are enforced rather than intended:

- the report's architecture section reads the **same** `buildDependencyGraph()`
  model the React Flow diagram renders (one build, two consumers), so the
  coupling it describes is the coupling the picture draws;
- score formatting lives in `v2/src/lib/scoring/format.ts`, used by both the
  scorecard and the report, so a number cannot read two ways.

Indexed source files come from one grouped, owner-joined read over `chunks`
(`v2/src/lib/report/sources.ts`) that selects a path, a document type and a
chunk count — never a chunk body.

As rendered, the report is a **chapter of the assessment surface** rather than a
document embedded in it: its container spans the dashboard, the masthead carries a
subtitle and one metadata line built from the sections' own counts, the executive
summary puts its lede beside its supporting paragraphs, the key takeaways are a two-up
card grid, and findings are rows with their counted evidence and Ask control in a right
column. Readability is a measure on the *text* (~79 characters), never a cap on the
container — see [Presentation and theme](#presentation-and-theme).

## Sample fixture

The sample project lives at `fixtures/sample-legacy-api`. It is a small,
synthetic, checked-in legacy Java EE system used for local
development, automated tests, demonstrations and screenshots. Three
services with a synchronous call chain and one external integration:

```
customer-service ──► order-service ──► payment-service ──► external gateway
```

It is deliberately built to contain the things an assessment is supposed to
notice: REST controllers, service classes, JDBC repositories, synchronous
service-to-service calls, configuration files, a service with no test tree
at all, denormalized and money-as-float data problems, and one service
(`payment-service`) that needs major restructuring rather than a
lift-and-shift.

Load it without preparing a ZIP by hand:

```bash
pnpm seed:sample
```

The command packs the fixture into an archive and submits it through
**exactly the path an upload takes** — same extraction guards, same
chunker, same duplicate detection, same embeddings, same store. A fixture
loaded by a shortcut would only be testing the shortcut.

```bash
pnpm seed:sample                       # owner "sample-fixture"
pnpm seed:sample --owner <sessionId>   # a different owner
pnpm seed:sample --override            # ingest a second copy anyway
```

To produce a **completed run** for the seeded project without an API key —
useful for demos and screenshots:

```bash
pnpm demo:run                          # attaches the "healthy" operational fixture
pnpm demo:run --operational degraded   # the other direction: worse measured operations
pnpm demo:run --operational none       # no operational data: code-only estimates
```

This runs the analysis against the fixture's checked-in expectation file
(`fixtures/sample-legacy-api.expected.json`) instead of a model. Every
narrative it writes is prefixed
`[DETERMINISTIC DEMO RUN — ... no model was called]`, so a demo run can
never be mistaken for one the pipeline inferred from the code. It prints the
resulting five scores read back from the database, and — because it attaches
the operational fixture by default — it demonstrates the refinement as well:
the code-only baseline is printed next to the refined scores. Recorded from
this working tree, on the same persisted findings:

```
code-only baseline   readiness 33.2 · risk 83.3 · effort 5.1 · cost USD 711,000
"healthy"  attached  readiness 36.1 · risk 71.6 (−11.7 from operational data)
"degraded" attached  readiness 29.9 · risk 97.1 (+13.8 from operational data)
```

The operational fixtures at `fixtures/sample-legacy-api.operational/{healthy,degraded}/`
are ordinary attachments — `app.log`, `health.json`, `incidents.json` — and are
the same files the tests read, so a fixture that only exists inside a test
cannot pass for a working upload path.

The source fixture is used as deterministic test data too: its structure is
asserted against the fixture's source in `v2/src/lib/scoring/sample-fixture.test.ts`,
so the expectation and the Java files cannot drift apart.

## Known limitations

Stated plainly, because a project whose limitations are missing is a
project whose claims cannot be checked. Everything below is current, and
each item is recorded in `PROJECT_STATUS.md` with its evidence.

1. **The dependency graph renders incorrectly — and the failure mode has changed
   since it was first recorded.** When it was first measured, nodes stayed
   `visibility: hidden` and no edge paths existed at all (hydration, CSS loading,
   container sizing and the dev-origin restriction were ruled out). A later browser
   check on the demo project found something different: **all four nodes render**
   (visible, labelled, risk-coloured, 256px) and **three edge paths are emitted** with
   the right stroke colours and real `d` geometry — but that geometry arcs above the
   node row instead of joining node to node, a small unstyled control rectangle sits
   at the canvas's left edge, and the canvas reserves ~200px of height for ~40px of
   content. The graph *model* (`v2/src/lib/graph/build-graph.ts`) is correct and fully
   unit-tested — the defect is in the rendering layer, and the model must not be
   rewritten to work around it. The presentation work deliberately changed only the
   surrounding chrome (heading, separator, well surface).
2. **No model run has completed against a live API.** The pipeline has been
   exercised end to end with a scripted model and a real database, and its
   failure path has been verified against a real HTTP call (an invalid key
   produced a clean `failed` run with the failing stage recorded). The
   credential in the working tree is still invalid, and it was not re-tested
   in the latest round. No narrative has been produced by the real DeepSeek
   API. Ollama embeddings *have* been exercised for real.
3. **Comparison has no ground truth to compare against.** Ground-truth
   directories are excluded from ingestion, so the evaluator grades
   internal consistency rather than correctness against a known answer,
   and any gap it reports downgrades a scorecard's evidence quality to
   `partial`.
4. **The trace viewer renders, but its read path is untested.** `/admin/traces`
   builds as a dynamic route, its waterfall model is covered by 18 unit tests, a
   labelled fixture trace is always shown, and the page has been loaded in a browser
   against spans the application wrote to Postgres. What is still missing is a test of
   `trace-store.ts` (the Postgres query layer) — there is none — and real spans would
   render a **numeric** span kind, because the exporter stores `String(span.kind)`. Spans carry no owner id, so the page is gated behind
   `ADMIN_TRACES_ENABLED` rather than scoped per session, and it has no live
   tail (spans still buffered are not shown; the list caps at 20 traces).
5. **M7 (polish) is implemented and unit-tested, and browser-covered only in part.**
   Built: the analysis report and its expand-in-place sections; per-service findings
   as one disclosure per service, reachable without the graph; the dependency list as
   text; the theme and the report's full-width composition; the Ask handoff from
   sections and findings; the analysis-progress lifecycle (persisted stages, polling,
   automatic refresh when a run finishes); loading states; error states that separate
   "nothing is there" from "I could not read it"; an owner-scoped not-found page; and
   the accessibility gaps in these surfaces. Rendered and inspected at 1680 / 1100 /
   414px on the seeded demo project: the page, scorecard, report, dependency list,
   graph canvas and `/admin/traces`. **Not** rendered or driven: the error panel, the
   not-found page, the loading skeleton, the in-flight progress display, any
   click-to-expand, and a screen-reader pass. The graph's rendering defect is separate
   and still open (item 1).
6. **Operational data moves Risk only.** Data volume and restart counts are
   reported next to the adjustment but deliberately not scored, because no
   defensible threshold for them was established; log evidence is penalty-only;
   free-text incident reports are counted by declared severity keywords, which
   the rendered detail states.
7. **Refinement is measured data, never model output — and not every parameter
   is an input.** Target environment and provider are recorded and shown but do
   not enter the cost formula (an infrastructure cost delta by target is not
   implemented). A budget is compared against the computed cost and never lowers
   it. A refinement changes the five numbers and nothing else: the narratives stay
   as the analysis wrote them.
8. **Browser coverage is partial, and the gaps are specific.** What has been
   rendered and inspected (on the seeded demo project, at three widths): the home
   page and its empty state, the upload card, the project row, the scorecard with its
   six metric tiles, the Analysis Report — all eight section rows, counts strips,
   findings, evidence disclosures and Ask controls — the dependency text list, the
   graph canvas, the refinements row, the ask bar, the environment footer and
   `/admin/traces`. What has **not**: the error panel, the not-found page, the loading
   skeleton, the analysis-progress display while a run is actually in flight, any
   interaction driven by hand, and anything on a project other than the demo one. No
   live model call has ever completed, and no disclosure or Ask control has been
   clicked in a browser.
9. **Stale runs are never reaped.** A run left `pending` or `running` by a
   process that died stays that way; there is no startup sweep.
10. **Scorecards are computed on read, not persisted.** The `scorecards` table
    exists from M0 and is still never written — recomputation is instant and
    cannot go stale. M5 persists the *inputs* (operational data and migration
    parameters) rather than the results, which is where the "user-adjusted
    assumptions" the schema was designed for actually live.
11. **No authentication, and nothing pretending to be.** Projects are scoped to an
    anonymous session cookie by design. There is no login, no account model, no OAuth
    provider, no magic link and no RBAC — the schema has `ownerId` and nothing else, and
    the id is a visibility scope rather than a credential, so it must not be described
    as a security boundary. Spans carry no owner id, which is why `/admin/traces` is
    gated behind `ADMIN_TRACES_ENABLED` instead of being session-scoped.

### Troubleshooting

- **`pnpm dev` reports the port is in use, or the page loads without
  styles or interactivity.** Check nothing else holds port 3000
  (`lsof -nP -iTCP:3000 -sTCP:LISTEN`) and start on another port:
  `pnpm dev --port 3001`. Browse it as `http://localhost:3001` — Next.js
  dev blocks other origins from its dev resources, and `http://[::1]:3001`
  is rejected as cross-origin, which leaves the page server-rendered but
  never hydrated.
- **Seeding fails with a connection error.** Ollama must be running and the
  model pulled: `docker compose up -d ollama && docker compose exec ollama
  ollama pull nomic-embed-text`. The seed command prints this hint when it
  detects the failure.

## Why V2 exists

V1's dashboard navigation mirrored its five backend services one-to-one
(Chat tab, RAG Q&A tab, Tools Chat tab, Agent Pipeline tab, Reports tab)
— which meant using the product required understanding the *backend's*
organizing principle, not just what you were trying to do. V2 is a
ground-up product rethink around actual user journeys instead, on a
stack better suited to the result. Full reasoning in
`PROJECT_PLAN_V2.md`.

V1 isn't deprecated because it was wrong — it did exactly what it was
built for (demonstrate each Spring AI capability cleanly, in isolation).
It's kept, intact and documented, both as a reference and because the
Java/Spring AI engineering it demonstrates remains a legitimate,
separate piece of work worth showing on its own terms.
